# Как устроена серверная версия TaskForge

## Путь запроса

Компонент Vue вызывает метод `useWorkspace`, например `saveTask`. API-клиент сериализует задачу в JSON и отправляет POST или PUT. Fastify проверяет сессию, параметры и тело запроса, затем ищет доску с нужным `owner_id`. Только после этого выполняет SQL. Клиент получает ответ и перечитывает задачи; при ошибке форма остаётся открытой.

Один сервер отдаёт `/api`, WebSocket и собранный frontend по `/taskforge-kanban/`. В разработке статические файлы отдаёт Vite, который проксирует API и WebSocket. CORS не нужен, поскольку для браузера это один origin.

## Почему эти инструменты

Node.js позволяет писать сервер на JavaScript/TypeScript. Fastify даёт маршруты, hooks, схемы валидации и удобный `inject` для тестов. TypeBox описывает входные данные одновременно для TypeScript и JSON Schema: статические типы не заменяют проверку непроверенного HTTP-ввода.

PostgreSQL хранит связанные сущности и поддерживает транзакции. `pg` использует пул соединений; `$1`, `$2` в запросах отделяют пользовательские данные от SQL. Небольшой проект обходится без ORM. Регистрация пользователя, создание первой доски и заполнение примерами выполняются в одной транзакции: при ошибке не остаётся частично созданного аккаунта.

Vue frontend оставлен прежним: добавление Node.js не требует переписывать работающий интерфейс на React. TypeScript используется в новом backend; это не означает, что весь frontend переведён на TypeScript.

## Данные

- `users`: UUID, уникальный email, имя, хеш пароля.
- `boards`: UUID, владелец, название, время создания.
- `tasks`: UUID, связь с доской, JSONB с полями задачи, время создания. JSONB удобно сохраняет теги и подзадачи; для сложной аналитики структуру стоило бы нормализовать.
- `sessions`: SHA-256 от session ID, JSON сессии, время истечения. Исходный session ID не хранится в таблице открытым текстом.

Внешние ключи связывают пользователя, доски и задачи; индекс на `tasks.board_id` помогает получать задачи конкретной доски.

## Авторизация и права

При регистрации пароль превращается в `salt:hash` с помощью `crypto.scrypt`. При входе вычисляется тот же хеш и сравнивается через `timingSafeEqual`. Пароль обратно не расшифровывается.

После успешного входа сервер меняет session ID и сохраняет `userId` в PostgreSQL. В браузер уходит подписанная cookie; JavaScript её не читает из-за HttpOnly. Серверная сессия отличается от JWT: её можно немедленно отозвать, удалив запись при выходе. Истёкшие записи не принимаются и периодически очищаются.

Знание UUID чужой доски не даёт доступа: каждый запрос проверяет пару `board.id + owner_id`. Сервер отвечает 404, не раскрывая наличие чужой доски. Это покрыто API-тестами для чтения, создания, изменения, переноса, удаления и сброса задач.

CSRF-защита сочетает SameSite=Strict, проверку Origin и нестандартный заголовок изменяющих запросов. WebSocket отдельно проверяет Origin и владельца до upgrade. Небраузерный клиент может подделать Origin, поэтому он не заменяет авторизацию.

## Обновления в реальном времени

После изменения задачи сервер отправляет подписчикам этой доски `board.changed`. Сами задачи не передаются в событии: вкладка перечитывает их обычным API, который снова проверяет права. При разрыве клиент переподключается с увеличивающейся задержкой до 10 секунд. После подключения запрашивает актуальный список, компенсируя пропущенные события.

Сервер использует ping/pong, удаляет мёртвые подключения, закрывает их по истечении сессии и при выходе. Клиент при закрытии с кодом 1008 возвращается к форме входа. Рассылка в памяти рассчитана на один процесс: она не синхронизирует отдельные реплики сервера.

## Тестирование

`server/test/api.test.ts` использует настоящий PostgreSQL в отдельной случайной схеме. Fastify `inject` вызывает маршруты без отдельного сетевого порта, но SQL, хеширование, cookie и права доступа настоящие. `injectWS` проверяет WebSocket. Подмена БД на массив в этих тестах не используется.

Playwright запускает браузер и проходит полный путь через интерфейс, HTTP и БД. Отдельный CI job выполняет те же сценарии против production-сборки в Docker Compose. Демо-тесты остаются независимыми от backend.

## Что важно уметь объяснить

1. Почему TypeScript не проверяет входящие JSON-данные во время выполнения.
2. Чем аутентификация отличается от проверки владельца ресурса.
3. Зачем менять session ID при входе и почему cookie HttpOnly не решает CSRF сама по себе.
4. Где проходит транзакция регистрации и что произойдёт при ошибке INSERT.
5. Почему после события WebSocket выполняется GET и зачем повторный GET после reconnect.
6. Почему это обычный backend, а не BFF: он владеет своей БД, а не агрегирует ответы микросервисов.
7. Что потребуется при масштабировании: брокер событий, контроль конкурирующих изменений, миграции, наблюдаемость и резервное копирование.
