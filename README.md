# TaskForge Kanban

Kanban-доска на Vue 3 с backend на Node.js и TypeScript. Полная версия хранит аккаунты, доски, задачи и сессии в PostgreSQL. WebSocket сообщает об изменениях доски другим открытым вкладкам.

[Демо на GitHub Pages](https://vlad1k22.github.io/taskforge-kanban/) работает без сервера и сохраняет задачи только в браузере. Регистрация и серверное хранение доступны при запуске полной версии.

## Возможности

- Создание, редактирование и удаление задач.
- Перемещение задач между колонками через drag-and-drop.
- Поиск по названию, описанию и тегам.
- Фильтры по приоритету, исполнителю, тегу и просроченным задачам.
- Чеклист внутри карточки задачи.
- Дедлайны, оценка времени и исполнители.
- Статистика по доске: всего задач, в работе, просрочено, процент выполнения.
- Полная версия: регистрация, вход, выход, несколько личных досок, серверное хранение и синхронизация вкладок.
- Изоляция данных: пользователь может читать и изменять только свои доски.
- Демо-режим: сохранение состояния в `localStorage` без аккаунта.
- Адаптивный интерфейс для desktop и mobile.

## Технологии

- Frontend: Vue 3, Vite, JavaScript, CSS, @lucide/vue.
- Backend: Node.js, TypeScript (strict), Fastify, TypeBox, PostgreSQL (`pg`), WebSocket.
- Проверки: `node:test`, Playwright, GitHub Actions; запуск полной версии в Docker Compose.

## Полная версия через Docker

Нужен Docker с Compose и работающим Docker Engine (например, запущенный Docker Desktop). Node.js на компьютере для этого способа не требуется.

1. Скопируйте `.env.example` в `.env`: `cp .env.example .env`, в PowerShell — `Copy-Item .env.example .env`.
2. Для использования вне локальной разработки замените `SESSION_SECRET` на случайную строку длиной не менее 32 символов и пароль БД. Секрет можно получить командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. При ручном указании `DATABASE_URL` специальные символы пароля требуют URL-кодирования.
3. Выполните:

```bash
docker compose up --build -d --wait
```

Откройте **http://localhost:3001/taskforge-kanban/** и зарегистрируйтесь. При регистрации создаётся личная доска с пятью примерами задач; новые доски пустые. Это не совместные доски: синхронизируются вкладки одного владельца.

Остановка: `docker compose down`. Данные остаются в Docker volume. Порты `3001` и `5434` должны быть свободны; PostgreSQL опубликован только на loopback для локальной разработки и тестов.

## Локальная разработка

Нужен Node.js 22.19+ или 24 LTS. Скопируйте `.env.example` в `.env`. Запустите БД (`docker compose up -d db`) либо используйте установленный PostgreSQL 16+ и укажите его `DATABASE_URL`. Затем:

```bash
npm ci
npm run dev:full
```

Откройте **http://127.0.0.1:5173/taskforge-kanban/**. Vite проксирует `/api` и WebSocket в backend на `3001`; браузер обращается к одному origin. Схема БД создаётся при первом старте сервера. `.env` и данные БД не входят в репозиторий.

Для локального запуска собранной полной версии: `npm run build:full`, затем `SERVE_STATIC=true npm run start:server` (PowerShell: `$env:SERVE_STATIC='true'; npm run start:server`). Адрес — `http://localhost:3001/taskforge-kanban/`.

## Демо без backend

```bash
npm ci
npm run dev
```

Это тот же автономный режим, что на GitHub Pages. `npm run build` собирает демо; `npm run build:full` — полную версию. Значение `VITE_BACKEND_ENABLED=true` задаётся при сборке, а не после неё.

## Проверки

Для API-тестов нужна работающая PostgreSQL на `127.0.0.1:5434` с параметрами из примера. Другую БД можно задать через `TEST_DATABASE_URL`. API-тесты создают и удаляют только собственную случайную схему; браузерные тесты создают тестовые аккаунты в выбранной БД. Не запускайте их на production-базе.

```bash
npm run check:server
npm run build:server
npm run test:api
npx playwright install chromium
npm run test:e2e
npm run test:e2e:full
```

API-тесты проверяют регистрацию, хеширование паролей, смену сессии при входе, валидацию, CRUD, CSRF-защиту, изоляцию данных, сохранность данных между экземплярами сервера, WebSocket, выход и истечение сессии. Пять прежних e2e-сценариев проверяют автономную доску. Отдельные full-stack e2e проверяют регистрацию/вход, хранение на сервере, выбор доски, синхронизацию вкладок, восстановление после разрыва связи, выход, редактирование/удаление, ошибку сохранения с повторной отправкой и мобильный интерфейс.

Playwright сам запускает тестовые серверы: демо на `4174`, полную версию на `4175` и backend на `3001`. Для проверки уже запущенной сборки задайте `FULL_BASE_URL=http://127.0.0.1:3001/taskforge-kanban/` перед `npm run test:e2e:full`.

GitHub Actions запускает проверки демо, API и полной версии. Отдельный job собирает Docker-образ, поднимает Compose и выполняет браузерные тесты уже против контейнера. Workflow GitHub Pages продолжает публиковать только автономное демо.

## Архитектура и ограничения

- `useWorkspace` объединяет состояние интерфейса, API и подключение WebSocket; в демо использует localStorage. Авторизационные данные в localStorage не записываются.
- Сессии хранятся в PostgreSQL; браузер получает подписанную HttpOnly/SameSite=Strict cookie. Пароли хешируются `scrypt` со случайной солью. Session ID меняется при входе; выход отзывает сессию и закрывает её WebSocket-подключения.
- Сервер проверяет владельца доски на каждом endpoint, валидирует входные данные по TypeBox/JSON Schema и использует параметризованные SQL-запросы. Для изменяющих запросов нужны специальный заголовок и разрешённый origin; WebSocket отдельно проверяет origin и сессию. Есть ограничение частоты запросов.
- В событии WebSocket передаётся только ID изменившейся доски, затем клиент перечитывает задачи через авторизованный API. Есть heartbeat, переподключение и перечитывание после восстановления связи.
- Это учебный full-stack проект, **не BFF над микросервисами**. Рассылка событий работает внутри одного процесса Node.js; для нескольких реплик потребуется брокер. При одновременном редактировании действует последнее сохранение, версионирования нет.
- Скрипт инициализации создаёт исходную схему через `CREATE TABLE IF NOT EXISTS`; система версионированных миграций пока не внедрена. Для публичного размещения нужны HTTPS, `SECURE_COOKIE=true`, собственные секреты, корректный `APP_ORIGINS`, резервное копирование и дополнительная эксплуатационная настройка. Стандартные пароли в примере предназначены только для локального запуска.

Подробный разбор реализации: [docs/architecture.md](docs/architecture.md).
